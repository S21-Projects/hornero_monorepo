# Donacion Entrega Codigo Specification

## Purpose

Define delivery confirmation for a `donacion` by mutual short-lived code exchange: each party
(donante, referente) generates its own 6-digit one-time code, rendered as a QR and available as a
typed fallback, which the counterpart must present to confirm receipt. This capability REPLACES
the existing unconditional `confirmar-entrega` button (`DonacionService.confirmarEntrega`) — a
donación reaches `ENTREGADA` only after both parties' codes are independently verified. It reuses
the `OtpService`/`OtpThrottle` pattern (BCrypt hash, TTL, throttled resend, bounded attempts)
already proven for email verification.

## Requirements

### Requirement: Delivery Code Generation

The system MUST allow the donante and the referente of a donación in `ACEPTADA`, `EN_CAMINO`, or
`PENDIENTE_CONFIRMACION` state to generate their own 6-digit delivery code, independently of the
counterpart, on the confirmation screen at the moment of handoff. Each code MUST be persisted only
as a BCrypt hash, MUST carry a 10-minute TTL from the moment it is generated (not from dispatch or
donation creation), and MUST be scoped to exactly one donación and one party (donante or
referente) — a code generated by one party MUST NOT verify the other party's presentation.

#### Scenario: Donante generates a delivery code

- GIVEN a donación in `EN_CAMINO` state
- WHEN the donante opens the confirmation screen and generates a code
- THEN a 6-digit code is created, its BCrypt hash persisted with `expiraEn` 10 minutes ahead
- AND the plaintext code is returned once to the donante's client for QR rendering, never
  persisted in plaintext

#### Scenario: Referente generates a delivery code independently

- GIVEN the same donación, before the donante has generated a code
- WHEN the referente opens their confirmation screen and generates a code
- THEN a separate code is created for the referente, independent of whether the donante has
  generated theirs

#### Scenario: Code cannot verify against the wrong party

- GIVEN the donante's code and the referente's code both exist for a donación
- WHEN the referente presents the donante's own code back
- THEN verification fails — a party's code is only valid when presented BY the counterpart

### Requirement: QR Rendering and Typed Fallback

The system MUST render each generated code as a scannable QR encoding that same 6-digit value —
never an independent token — and MUST always offer a typed 6-digit input as an equivalent
fallback. Both the QR and the typed path MUST verify through the identical backend check.

#### Scenario: QR encodes the plain code

- GIVEN a generated delivery code "482913"
- WHEN its QR is decoded
- THEN the decoded value is exactly "482913"

#### Scenario: Typed fallback verifies identically to a scan

- GIVEN a party without camera access
- WHEN they type the 6-digit code shown by the counterpart instead of scanning it
- THEN the verification outcome is identical to a successful scan of the same code

### Requirement: Regenerating a Code Invalidates the Previous One Immediately

The system MUST invalidate a party's previously issued, unverified code the instant a new one is
generated for the same party and donación — the old code MUST NOT verify successfully afterward,
even if still within its original TTL.

#### Scenario: Regenerate burns the old code immediately

- GIVEN a donante's code generated 2 minutes ago, still within its 10-minute TTL
- WHEN the donante taps "Generar código nuevo"
- THEN the old code becomes permanently invalid
- AND a new code with a fresh 10-minute TTL is issued

#### Scenario: Regenerate after expiry issues a fresh code

- GIVEN a donante's code has passed its 10-minute TTL
- WHEN the donante taps "Generar código nuevo"
- THEN a new code is issued exactly as a first generation would be

### Requirement: Resend/Regenerate Throttling

The system MUST throttle how often a party may regenerate their own code, mirroring
`OtpThrottle`'s cooldown window, and MUST reject a regenerate request made before the cooldown
elapses with `429 ESPERA_ANTES_DE_REENVIAR`.

#### Scenario: Rapid regenerate is throttled

- GIVEN a donante just generated a code seconds ago
- WHEN they immediately tap "Generar código nuevo" again before the cooldown window elapses
- THEN the request is rejected with `429 ESPERA_ANTES_DE_REENVIAR`
- AND the previous code remains valid and unaffected

### Requirement: Bounded Verification Attempts

The system MUST count failed verification attempts per issued code and MUST reject the code as
permanently invalid once the configured maximum attempts is reached, mirroring `OtpService`'s
`maxAttempts` behavior, independent of remaining TTL.

#### Scenario: Wrong code exhausts attempts

- GIVEN a referente's code with the configured max attempts (e.g. 5)
- WHEN the counterpart submits an incorrect 6-digit value that many times
- THEN the code is invalidated
- AND the referente must generate a new code to continue

#### Scenario: Correct code after some wrong attempts still succeeds

- GIVEN a code with 2 failed attempts recorded, below the max
- WHEN the correct code is submitted next
- THEN verification succeeds

### Requirement: Expired Code Is Rejected

The system MUST reject verification of a code whose TTL has elapsed with a distinct outcome from
"wrong code" (mirroring `OtpService`'s `410 CODIGO_EXPIRADO`), and MUST NOT count an expired
presentation against the attempt limit.

#### Scenario: Expired code rejected without consuming an attempt

- GIVEN a code generated 11 minutes ago (past its 10-minute TTL)
- WHEN the counterpart presents it, correctly typed
- THEN the verification is rejected as expired, not as incorrect
- AND the attempt counter for that code is unchanged

### Requirement: Mutual Verification Required for `ENTREGADA`

The system MUST transition a donación to `ENTREGADA` only when BOTH the donante's code has been
verified by the referente AND the referente's code has been verified by the donante. Verifying
only one side MUST move the donación to `PENDIENTE_CONFIRMACION` (or keep it there), exactly
mirroring the existing dual-confirmation semantics of `confirmarEntrega`, but gated by code
verification instead of a bare button press.

#### Scenario: Only one side verified stays pending

- GIVEN a donación in `EN_CAMINO`
- WHEN the referente successfully verifies the donante's code, but the donante has not yet
  verified the referente's code
- THEN the donación moves to `PENDIENTE_CONFIRMACION`
- AND does not reach `ENTREGADA`

#### Scenario: Both sides verified reaches ENTREGADA

- GIVEN a donación in `PENDIENTE_CONFIRMACION` with the referente's code already verified by the
  donante
- WHEN the donante's code is now also verified by the referente
- THEN the donación transitions to `ENTREGADA`
- AND `fechaEntrega` is set to the current date

#### Scenario: Verifying twice on the same side is idempotent

- GIVEN the referente already successfully verified the donante's code
- WHEN the referente's client resubmits the same verification (e.g. retry after a dropped response)
- THEN the donación state is unchanged and no error is raised for the already-satisfied side

### Requirement: `TRANSICIONES_PERMITIDAS` Gains Delivery-Code Entries

The system MUST add explicit entries to `TRANSICIONES_PERMITIDAS`
(`DonacionService.java:36-46`) for the code-verified path so that `ACEPTADA`/`EN_CAMINO` →
`PENDIENTE_CONFIRMACION` → `ENTREGADA` are legal, explicit transitions rather than a bypass of the
table.

#### Scenario: Delivery transition table entries exist

- GIVEN the transition table as implemented after this change
- WHEN `PENDIENTE_CONFIRMACION` and `ENTREGADA` are looked up as transition sources/targets
- THEN they appear with the same explicitness as `OFRECIDA`/`ACEPTADA`/`EN_CAMINO` entries — no
  code path bypasses the table to reach these states outside of `overrideEstado`

### Requirement: Retirement of the Unconditional Confirm Action

The system MUST remove the plain `confirmar-entrega` endpoint and its UI button once the
code-verified path ships (delivered together, per the proposal's slice 3c rollout so no deployed
UI ever calls a retired endpoint). After retirement, no client-authenticated request MUST be able
to move a donación to `ENTREGADA` without code verification, except through the ADMINISTRADOR
override path.

#### Scenario: Old confirm endpoint no longer exists

- GIVEN the delivery-code path has shipped and the old endpoint has been retired
- WHEN a request is made to the old `confirmar-entrega` route
- THEN the request fails (404/410 or equivalent) — no code path resolves to the retired handler

#### Scenario: No bare confirmation reaches ENTREGADA

- GIVEN a donación in `EN_CAMINO` with no codes generated
- WHEN either party attempts to mark it delivered without presenting the counterpart's code
- THEN the request is rejected

### Requirement: Only the Donante and Referente Parties May Generate or Verify Codes

The system MUST restrict code generation and verification to the donante who owns the donación and
the referente of the organizacion receiving it. An ADMINISTRADOR MUST NOT generate or verify a
delivery code on behalf of either party — the override path remains the only admin-driven state
change.

#### Scenario: Unrelated donante is denied

- GIVEN a donación belonging to donante A
- WHEN donante B requests to generate a code for it
- THEN the request is rejected (403 or equivalent)

#### Scenario: Non-owning referente is denied

- GIVEN a donación assigned to organizacion X
- WHEN a referente who does not own organizacion X requests to generate or verify a code for it
- THEN the request is rejected (403 or equivalent)

### Requirement: ADMINISTRADOR Override Path Kept Unchanged

The system MUST keep `DonacionService.overrideEstado` functioning exactly as before this change:
an ADMINISTRADOR MAY still force a donación to any valid state with a recorded `motivo`, bypassing
code verification entirely, and this path MUST NOT generate, verify, or invalidate any delivery
code as a side effect.

#### Scenario: Admin override still resolves a stuck donación

- GIVEN a donación stuck in `PENDIENTE_CONFIRMACION` because one party lost their device
- WHEN an ADMINISTRADOR overrides it to `ENTREGADA` with a motivo
- THEN the donación reaches `ENTREGADA`
- AND no delivery code record is created, verified, or altered by the override

### Requirement: Mobile Delivery Confirmation Screen

The system MUST provide a mobile-usable confirmation screen, reachable by both the donante and the
referente for a donación in an active delivery state, that displays: the party's own current code
as a QR with a live countdown to expiry, a typed-code input to submit the counterpart's code, both
parties' confirmation status (verified / not yet verified), a "Escanear código" scanning action,
and a "Generar código nuevo" action.

#### Scenario: Screen reflects live countdown

- GIVEN a code with 90 seconds remaining before its 10-minute TTL elapses
- WHEN the confirmation screen is open
- THEN a countdown visibly ticks down toward expiry
- AND on reaching zero the code is shown as expired with "Generar código nuevo" available

#### Scenario: Screen reflects the counterpart's confirmation status

- GIVEN the referente has already verified the donante's code
- WHEN the donante views their confirmation screen
- THEN it shows the referente's side as confirmed and the donante's own side as pending until they
  verify the referente's code

#### Scenario: Scanning updates status without a page reload

- GIVEN a party scans the counterpart's QR successfully
- WHEN verification succeeds
- THEN the screen updates that side's status immediately, without a full page reload
