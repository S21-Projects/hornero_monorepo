# Design: Rondas on Live Data (rondas-datos-vivos)

## Technical Approach

Exploration Approach 1, as chained PRs (stacked-to-main, merged in order). The MS owns the live
vulnerability number because it owns the data; the worker becomes a stateless solver plus a geometry
lookup. The worker contract v1 already carries `codigoRadio` and `deficit` per candidate, and the
worker's `PROVISTO` branch wins over every CSV fallback (`internal/geo/deficit.go:114`), so no
contract version bump is needed.

- **PR1 (MS)**: `poblacion_radio` table (V011 + read-only entity) and a re-runnable import; one grouped
  native query per ronda returns per-radio counts; a pure Java function computes the median and
  `v`; `EntradaRondaFactory` fills `codigoRadio` and `deficit`.
- **PR2 (worker)**: `serve` runs with an empty `Resolvedor` (no CSV); new `POST /v1/radio` over a
  simplified 2022 radios asset (NDJSON + gzip, generated by DuckDB). PR2 may be split into PR2a
  (serve without CSVs) and PR2b (`/v1/radio`) if the task forecast exceeds 400 lines.
- **PR3 (MS)**: `RadioCensalClient` resolves `codigo_radio` synchronously on `crear`/`actualizar`
  when coordinates change (best-effort), plus an hourly self-healing backfill job.

Spec reference: `specs/ronda-vulnerabilidad-viva/spec.md`. The `organizacion-radio-censal` and
`ronda-asignacion` deltas follow the decisions below.

## Architecture Decisions

### AD-1: `poblacion_radio` owned by V011, mapped by a read-only entity

**Choice**: `scripts/sql/V011__poblacion_radio.sql` creates
`poblacion_radio (codigo_radio varchar(9) PRIMARY KEY, habitantes integer NOT NULL CHECK (habitantes >= 0))`
with `CREATE TABLE IF NOT EXISTS`, in `BEGIN/COMMIT`. A matching `@Entity @Immutable PoblacionRadio`
(`org.example.domain`) maps the same columns.
**Alternatives considered**: script only (H2 test contexts would lack the table, since tests use
`ddl-auto=create-drop`); entity only (spec requires an additive `scripts/sql` migration, and the
import must be runnable before the new MS image boots).
**Rationale**: V011 satisfies the spec and lets `make importar-poblacion` run first; the entity keeps
H2 integration tests (`RondaServiceLazyLoadingIntegrationTest`, the new repository test) working.
Identical column definitions make `ddl-auto=update` a no-op on Postgres. No `EsquemaVerificador`
flag: an empty or missing table degrades every candidate to NEUTRAL, which is logged at ronda time
(AD-4), never a 5xx.

### AD-2: No index on `organizaciones(codigo_radio)`

**Choice**: do not add one.
**Alternatives considered**: `CREATE INDEX IF NOT EXISTS` in V011.
**Rationale**: the aggregate needs every comedor of every radio to compute the national median, so
it is a full grouped scan of `organizaciones` (~3k rows today, ~30k worst case) either way; an index
cannot prune it. Backfill filters on `codigo_radio IS NULL` with a small `LIMIT`, also fine without it.

### AD-3: Truncate-and-reload import through `COPY FROM STDIN`

**Choice**: `make importar-poblacion` (depends on `backup`) pipes `scripts/mapa/importar-poblacion.sh`
into the existing `$(PSQL)` (`docker compose exec -T postgres sh -c 'psql ... -v ON_ERROR_STOP=1'`).
The script writes one stream: `BEGIN; CREATE TEMP TABLE poblacion_staging (codigo_radio text,
habitantes integer, hogares integer) ON COMMIT DROP; COPY poblacion_staging FROM STDIN WITH (FORMAT
csv, HEADER true);`, then the CSV body of `go_algorithms_worker/data/poblacion-radios.csv`, then `\.`,
then `TRUNCATE poblacion_radio; INSERT ... SELECT lpad(codigo_radio, 9, '0'), habitantes FROM
poblacion_staging WHERE habitantes IS NOT NULL; COMMIT;` and a final row count.
**Alternatives considered**: host-side `\copy FROM 'file'` (psql runs inside the container, the file
is on the host, so the path does not resolve); `INSERT ... ON CONFLICT DO UPDATE` upsert (leaves rows
that disappeared from the dataset, so contents are not guaranteed identical); a DuckDB-generated SQL
file like `importar-renacom` (66.5k INSERT statements, needs DuckDB for no gain).
**Rationale**: inline `COPY FROM STDIN` is the `pg_dump` pattern and works through `exec -T`. Truncate
plus insert in one transaction yields byte-identical contents on every run (spec idempotency) and a
duplicate code aborts the whole run loudly through the primary key. The ACCESS EXCLUSIVE lock lasts
about a second; rondas are manual and rare.

### AD-4: Counts in SQL, median and formula in Java

**Choice**: one native query in `PoblacionRadioRepository.zonasConComedores(estadosOrg, estadosNec,
hoy)` returns `(codigo_radio, habitantes, comedores, necesidades)` for every radio with at least one
comedor and `habitantes > 0`. `VulnerabilidadCalculator` (mirrors `CumplimientoCalculator`) calls it
once and delegates to a pure static function that computes `hpc = habitantes / comedores`,
`median = percentile_cont(0.5)` semantics (mean of the two middle values for even counts), and
`v = hpc / median * (1 + necesidades / comedores)`. It returns `Map<String, Double>` for all those
radios.
**Alternatives considered**: `percentile_cont(0.5) WITHIN GROUP` inside the query (H2 dialect
support is a risk for the test suite, and the formula would only be testable against a database);
JPQL (two-level aggregation, necesidades per org then per radio, is awkward in JPQL).
**Rationale**: the query uses only CTE, `LEFT JOIN`, `GROUP BY`, `COALESCE`, which run identically on
Postgres and H2 (`MODE=PostgreSQL`). The spec scenario (2.25) becomes a plain unit test. Returning
all radios (at most ~30k entries) avoids an `IN (:radios)` with an empty-list edge case. When the
result is empty while candidates have radios, the calculator logs one WARN ("poblacion_radio empty or
no comedores with radio: run make importar-poblacion").

Query shape (estado values bound as string collections, same literals as `findMapa`):

```sql
WITH nec AS (
  SELECT n.organizacion_id, COUNT(*) AS abiertas
  FROM necesidades n
  WHERE n.estado IN (:estadosNec)
    AND (n.fecha_vencimiento IS NULL OR n.fecha_vencimiento >= :hoy)
  GROUP BY n.organizacion_id
), com AS (
  SELECT o.codigo_radio, COUNT(*) AS comedores, COALESCE(SUM(nec.abiertas), 0) AS necesidades
  FROM organizaciones o
  LEFT JOIN nec ON nec.organizacion_id = o.id
  WHERE o.estado IN (:estadosOrg)
    AND o.latitud IS NOT NULL AND o.longitud IS NOT NULL AND o.codigo_radio IS NOT NULL
  GROUP BY o.codigo_radio
)
SELECT com.codigo_radio, p.habitantes, com.comedores, com.necesidades
FROM com JOIN poblacion_radio p ON p.codigo_radio = com.codigo_radio
WHERE p.habitantes > 0
```

The "uncovered" necesidad definition is exactly `findMapa`'s: `ABIERTA`/`EN_PROGRESO` and not past
`fecha_vencimiento`. Radios with comedores but no population row are outside the median, matching
`scripts/mapa/vulnerabilidad.sql` (hpc NULL never enters the median).

### AD-5: NEUTRAL is signalled by omission, resolved by the worker

**Choice**: the factory always sends `codigoRadio` when the organizacion has one; it sends `deficit`
only when the map has a value. Otherwise `deficit` is omitted (`@JsonInclude(NON_NULL)`), and the
worker's `Resolvedor` answers. After PR2 the `serve` resolver is empty, so the answer is
`NEUTRAL 1.0`, recorded in the output's `deficitFuente` and persisted on `asignacion.deficit_fuente`.
**Alternatives considered**: send `deficit: 1.0` explicitly (the worker would record `PROVISTO`,
violating the spec's NEUTRAL `deficitFuente`); add a `deficitFuente` input field (contract change for
no benefit).
**Rationale**: zero contract change. Caveat: between deploying PR1 and PR2 the worker still has its
CSVs, so an omitted deficit may resolve to `RADIO`/`CERCANO` from the baked data. Deploy PR1 and PR2
together on the Pi (they are independent services); the NEUTRAL scenarios are satisfied end-to-end
once PR2 is deployed.

### AD-6: Aggregate runs inside RondaService transaction 1, through the factory

**Choice**: `EntradaRondaFactory` gains a `VulnerabilidadCalculator` collaborator and calls it once
in `crear(...)`, next to `cumplimientoCalculator.calcular()`. `RondaService` is unchanged.
**Alternatives considered**: compute in `RondaService.leer()` and pass a new map parameter.
**Rationale**: the factory already runs inside transaction 1 (read snapshot consistent with the
candidate list) and already hosts the analogous per-ronda grouped query; the factory signature and
every `RondaService` test stay untouched.

### AD-7: Worker `serve` without data; CSVs stay for the CLI

**Choice**: `serve --data` defaults to `""`; empty means `geo.NuevoResolvedor(nil, nil, 1.0)`
(nil-map lookups are safe in Go). `--data`/`--poblacion`/`--provincia` keep working when passed.
`metrics`/`assign` are unchanged. The Dockerfile copies only the radios asset and uses an exec-form
entrypoint `["./algorithms","serve","--addr",":8090","--radios","data/radios-2022.ndjson.gz"]`;
`POBLACION_CSV` leaves the Dockerfile and `docker-compose.yml`. The worker healthcheck
`start_period` goes from 10s to 30s (asset load on the Pi).
**Alternatives considered**: delete the CSV path from `serve` (breaks local experiments); keep
copying `data/` (ships stale numbers that could leak into rondas through RADIO/CERCANO).
**Rationale**: the image carries no scoring data, so live MS data is the only source.

### AD-8: Radios asset is gzipped NDJSON from DuckDB, committed under a size gate

**Choice**: new `scripts/mapa/radios.sql` + `make mapa-radios` (reuses `fetch.sh` cache):

```sql
COPY (
  SELECT lpad(COD_2022, 9, '0') AS c,
         ST_AsGeoJSON(ST_ReducePrecision(
             ST_SimplifyPreserveTopology(geometry::GEOMETRY, 0.0001), 0.00001))::JSON AS g
  FROM read_parquet('scripts/mapa/.cache/radios.parquet')
  ORDER BY 1
) TO 'go_algorithms_worker/data/radios-2022.ndjson.gz' (FORMAT json, COMPRESSION gzip);
```

One line per radio: `{"c":"020070101","g":<GeoJSON Polygon|MultiPolygon>}`.
**Size estimate** (to be measured as PR2's first task): 66.5k radios, ~15–30 vertices each after a
~10 m tolerance gives ~1–2M vertices; at ~22 chars per vertex that is ~22–44 MB of text and
roughly **8–17 MB gzipped**. A delta-varint binary would be ~3–7 MB but needs a custom packer and
format spec.
**Gate**: commit the asset if it is <= 10 MB. Above that, first raise the tolerance to 0.0002
(~20 m) and re-measure; if still above, publish it as a GitHub Release asset and fetch it in the
Dockerfile with a pinned SHA-256. The census vintage is static until the next census, so a
committed asset is regenerated essentially never; it is a generated file, excluded from the
authored-line review count.
**Alternatives considered**: custom binary (smaller, more code and a packer tool); full GeoJSON
FeatureCollection (one huge document, no streaming decode); fetching the 65 MB parquet at image
build (needs DuckDB on the Pi build).
**Rationale**: DuckDB-native output, stdlib streaming decode (`bufio` + `encoding/json` per line),
human-inspectable, deterministic ordering.

### AD-9: Point-in-polygon with bbox grid, even-odd rings, near-miss fallback

**Choice**: new package `internal/radios`:
- `Cargar(r io.Reader) (*Indice, error)` streams the NDJSON (caller wraps `gzip.NewReader`);
  `Polygon` and `MultiPolygon` become a list of polygons, each `[][][2]float64` (rings) plus bbox.
- Containment: even-odd ray casting across all rings of a polygon, so holes are handled without
  ring orientation logic.
- Index: uniform grid of 0.05 degree cells, `map[int64][]int32` of polygon ids per cell their bbox
  touches; a polygon whose bbox spans more than 400 cells goes to a `grandes` list checked by bbox on
  every query (large rural radios; a few hundred at most).
- Ties (a point on a shared edge matched by two radios): lowest code, as `build.sql` does.
- Near miss: per-polygon simplification opens gaps up to the tolerance between neighbours, and
  street-geocoded comedores sit exactly on radio borders (borders are streets). When no polygon
  contains the point, the nearest polygon edge within 2x tolerance (25 m, flat-earth meters at the
  point's latitude) wins; beyond that, not found.
- Memory: ~1–2M vertices as float64 pairs is ~16–32 MB plus index, well within a Pi 5. Load happens
  before `ListenAndServe`, so `/healthz` is green only once loaded.
**Alternatives considered**: R-tree (more code for no measurable gain at one lookup per org edit);
linear scan of 66.5k bboxes (fine for latency but wasteful); `ST_CoverageSimplify` to avoid gaps
(availability in the installed DuckDB spatial is unverified).
**Rationale**: stdlib only, small and testable with tiny synthetic polygons.

### AD-10: `POST /v1/radio` contract

**Choice**:

| Case | Status | Body |
|---|---|---|
| Found | 200 | `{"codigoRadio":"020070101"}` |
| Malformed JSON, missing/non-finite coords, lat outside [-90,90] or lng outside [-180,180] | 400 | `{"error":"ENTRADA_INVALIDA","detalle":...}` |
| No polygon within tolerance | 404 | `{"error":"RADIO_NO_ENCONTRADO",...}` |
| Asset not loaded (`--radios` empty or file missing) | 503 | `{"error":"RADIOS_NO_DISPONIBLES",...}` |
| Not POST | 405 | `METODO_NO_PERMITIDO` |

Request `{"latitud": -31.4167, "longitud": -64.1833}`, body capped with `http.MaxBytesReader` (4 KiB),
reusing `escribirError`. A missing asset logs a warning and keeps `serve` up: rondas never depend on
it. Worker-internal only (no host port), so no access-rule change in any layer.
**Alternatives considered**: `GET /v1/radio?lat=&lng=` (fine too; POST keeps the JSON style of
`/v1/ronda`); batch endpoint (backfill volume is small, single lookups suffice).

### AD-11: `RadioCensalClient` is a separate, never-throwing client

**Choice**: `org.example.organizacion.radio.RadioCensalClient` (`Optional<String> resolver(double lat,
double lng)`), `HttpRadioCensalClient` (RestClient on `${app.worker.url}/v1/radio`, connect 1s, read
2s; 404 returns empty at DEBUG; any other failure returns empty and logs WARN), and
`RadioCensalNoConfiguradoClient` (always empty). `RadioCensalConfig` picks one on `app.worker.url`,
exactly like `AsignadorConfig`.
**Alternatives considered**: extend `HttpAsignadorClient` (30 s read timeout and exception-based
contract are wrong for a best-effort lookup).
**Rationale**: same wiring pattern, separate failure semantics: resolution must never block or fail
an organizacion write.

### AD-12: Synchronous resolution inside the write transaction

**Choice**: `OrganizacionService.crear` resolves when both coordinates are present;
`actualizar` resolves only when latitud or longitud actually changed (`Objects.equals` against the
previous values). The result (or `null` on failure, since the old radio is stale for the new point)
is set before `save`, inside the existing `@Transactional`.
**Alternatives considered**: `@TransactionalEventListener(AFTER_COMMIT)` plus async update (a second
write races the user's next edit on `@Version` and adds threads to test); fire-and-forget.
**Rationale**: worst case adds the 2 s read timeout to a rare action; when the worker container is
down, the connection fails fast. Holding one pooled connection for up to 2 s is acceptable at this
scale. Simple and deterministic to test.

### AD-13: Backfill is an hourly self-healing job

**Choice**: `RadioCensalBackfillJob` (`@Scheduled(cron = "${app.radios.backfill.cron:0 15 * * * *}")`,
`app.radios.backfill.enabled` default true, `max-por-corrida` default 500) loads organizaciones with
coordinates and `codigo_radio IS NULL` ordered by id (any origen), and resolves each in its own
`TransactionTemplate`; an optimistic-lock conflict or empty result skips the row.
**Alternatives considered**: admin endpoint (needs MS `SecurityConfig`, BFF `@Roles` and SPA changes
for a one-off); startup runner (the MS does not `depends_on` the worker, so it would often run while
the worker is down); make target (the worker has no host port, so it would need `exec` plumbing).
**Rationale**: covers the initial backfill within an hour of deploy and retries every write whose
crear-time resolution failed because the worker was down. Orgs outside every radio are retried each
hour; that is bounded by the batch cap and costs one cheap lookup each. Mirrors the existing cron
job pattern (`RondaAutomaticaJob`, evidencia barrido).

## Data Flow

Ronda (PR1 + PR2):

    POST /api/rondas ─→ RondaService.ejecutar
        tx1: leer() ─→ EntradaRondaFactory.crear
                         ├─ CumplimientoCalculator.calcular()      (1 grouped query)
                         └─ VulnerabilidadCalculator.calcular(hoy)  (1 grouped query
                              organizaciones ⋈ necesidades ⋈ poblacion_radio → Java median/v)
             candidate: codigoRadio = org.codigoRadio; deficit = v | omitted
        no tx: HttpAsignadorClient ─→ worker POST /v1/ronda
                         Resolver: PROVISTO | (empty resolvedor) NEUTRAL 1.0
        tx2: persist asignacion.deficit_fuente / codigo_radio

Radio resolution (PR3):

    crear/actualizar (coords changed) ─→ RadioCensalClient ─→ worker POST /v1/radio
                                              200 code | 404/err/timeout → null
    hourly job: orgs(coords, radio NULL) ─→ same client ─→ per-row tx update

Import: `poblacion-radios.csv` ─→ importar-poblacion.sh ─→ `$(PSQL)` (staging → truncate → insert).

## Migration / Rollout

1. `make backup && make migrate` (V011), then `make importar-poblacion` (add `ENV_FILE=.env.local`
   locally). Order-independent with the MS deploy: the entity maps the same table.
2. Deploy PR1 and PR2 together on the Pi (AD-5 caveat), then PR3. After PR3, the backfill fills
   platform organizaciones within the first hour while the worker is up.
3. Ronda scores shift versus the baked CSV by design; `deficitFuente` per asignacion keeps them
   explainable.
4. Rollback: reverse merge order (see proposal). `poblacion_radio` can stay; `DROP TABLE
   poblacion_radio` is the documented rollback in `docs/db-changes.md`.
